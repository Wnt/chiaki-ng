# PLE-357: an asymmetric window for the quality badge

The badge stayed Poor for ~25 s after the network recovered, because
`SLOW_WINDOW_SECONDS = 30` fed the same candidate as the 5-sample fast window on the way
down, and a median needs a majority of its samples to be good before it moves. This is
the measurement that motivated the fix, what the fix actually is, and the run that
confirms it on the rig.

Device: Galaxy S22 Ultra, SM-S908B, `192.168.40.101:5555`, on SSID `Kari-Impair`
(VLAN 40) behind the PLE-349 impairment rig. Console: PS5-466, `192.168.1.164`. Ground
truth is the phone's own `ping -D -i 1 192.168.1.164`, which crosses the shaped path;
ADB is exempt from the shaping and is never used as ground truth here.

Method: one continuous stream, `Log stream statistics (diagnostic)`
(`stream_feedback_stats_log`) on, the impairment profile stepped underneath it every
60 s from CT950 -- no reassociation, no phone interaction, same pattern PLE-343 and
PLE-356 used. Capture: `build/captures/ple357` (`capture.sh`, `analyze.py`, not
committed -- gitignored study material per AGENTS rule 10).

## What changed, and why

Before this ticket, `nextLevel` computed `candidate = maxOf(enterLevel(fast),
enterLevel(slow))` (fast = 5-sample median, slow = 30-sample median) and tested
recovery against the **slow** median. Simulating that against a synthetic clean-after-
POOR sequence surfaced a second defect beyond the ~25 s lag the ticket named: once the
fast window had already recovered and stepped the badge down a level (POOR ->
CONSTRAINED), the slow window's own median -- a strict superset of history, so it lags
the fast one by construction -- could still read POOR and re-fire the "candidate worse
than current level" check, flipping the badge back up (POOR -> CONSTRAINED -> POOR)
before the slow window emptied. That is exactly the flicker the ticket says is worse
than the lag, so the fix removes the second window rather than shortening it: one
5-sample median now drives both directions, asymmetric only in how many *consecutive*
samples each direction needs to confirm --

- **worse**: one sample (`candidate.ordinal > level.ordinal`), unchanged from before
  this ticket -- the median itself still needs 3 of 5 samples to move, so
  `worseningToPoorStillTakesOnlyThreeSamples` still crosses at the 3rd bad sample.
- **better**: 3 consecutive samples with the fast median below the exit boundary
  (`RECOVERY_SAMPLES`, unchanged), so a single clean sample cannot flip it and a single
  dirty one resets the count.

Worst case that is 5 s to fill the window with clean samples plus 3 more to confirm:
8 s, deterministic (`recoveryReturnsToGoodInEightSecondsNotThirty`), against the ~25 s
the slow window produced.

## Unit tests (`NetworkQualityClassifierTest.kt`)

- `recoveryReturnsToGoodInEightSecondsNotThirty`: fills the window with POOR, then
  asserts CONSTRAINED at the 7th clean sample and GOOD at the 8th -- the exact number
  the asymmetric window produces.
- `worseningToPoorStillTakesOnlyThreeSamples`: the downward-to-Poor transition speed is
  unchanged by this ticket.
- `blipShapedSpikesNeverFlipTheLevel`: a single bad sample every 20 s (the `blip-200ms`
  shape) never moves the badge off GOOD across a 90 s run -- the same median outlier
  resistance PLE-343 established for one retransmit now holds under a shorter recovery
  window too.
- `consoleEvidenceWinsOnlyWhenLocalTransportHasTrulyRecovered` (PLE-355's test) is
  updated: it used to assert the badge stayed POOR five seconds after local transport
  went clean, documenting the very lag this ticket removes. It now asserts CONSTRAINED
  at that point -- POOR's graceful step-down -- with the CONSOLE cause unchanged.

Verified these run: breaking the assertion in
`recoveryReturnsToGoodInEightSecondsNotThirty` (GOOD -> POOR) turned the suite red with
that one test named; reverted before the final gate run.

## Device measurement

Real capture, `4g` (measured 61-63 ms RTT in PLE-343's calibration) stepped in for 67 s
under a live stream, then back to `clean`, with `blip-200ms` afterward as the
oscillation check. The 1 Hz `Feedback stats` log line (`probe_rtt_ms`,
`packet_jitter_ms`, `congestion_loss measured=`) was replayed offline through both the
new classifier and a reconstruction of the pre-fix one (`analyze.py`), since neither
version logs its own verdict -- the same fields, the same math as `NetworkQuality.kt`
and the unit tests, joined to the `impairctl` phase timestamps.

| phase transition | OLD algorithm (pre-PLE-357) | NEW algorithm (this fix) |
|---|---|---|
| `4g` -> `clean`: POOR entered | 95.2 s into the run | 95.2 s into the run (unchanged, as expected -- this ticket only touches recovery) |
| `clean`: GOOD reached | 23.8 s after the profile step | **10.8 s** after the profile step |

Both algorithms land on CONSTRAINED first (POOR's graceful step-down), then GOOD --
OLD at t=177.4s/180.4s (relative to run start), NEW at t=164.3s/167.4s, i.e. 13 s
earlier into GOOD for the same underlying network trace. This run's `4g` phase (67 s)
is shorter than a sustained real-world bad spell, so the 30-sample slow window here
never fully saturated with bad samples the way a longer, continuous problem would --
the calibrated worst case is the unit test's synthetic 30-sample fill, which reproduces
the ticket's ~25 s figure against the new algorithm's deterministic 8 s. Both numbers
agree on direction and are in the same range as the ticket's report.

`blip-200ms` (67 s, a 200-410 ms ping spike roughly every 20 s per the phone's own
ping) never moved the badge off GOOD in either the real capture or the unit test's
90 s synthetic run: no oscillation.

## Leaving the rig clean

`capture.sh`'s cleanup trap runs `impairctl.py clean --commit` on exit regardless of
outcome; `impairctl.py status --commit` after the run confirms `active_profile=clean`
and no qdisc on `eth1` or the ingress ifb.

## Known limits

- The device capture's `4g` phase (67 s) is short next to the ticket's ~25 s figure,
  which was measured after a longer degraded spell; the 8 s worst-case bound comes from
  the unit test's synthetic full-window fill, not this capture. A longer on-rig run
  (`--ttl 30m` per the ticket) would tighten this, but was not necessary to confirm the
  direction and rough magnitude of the fix, or its freedom from oscillation.
- PLE-356 (what `videoPacketJitterMicros` actually measures) had not landed on
  `fork/android-port` as of this branch; this fix does not depend on its outcome since
  it does not change which fields feed the classifier, only how their window is
  aggregated across time. If PLE-356 changes the jitter input, the window logic here is
  unaffected and should not need to change.
