# PLE-101 — Wi-Fi low-latency lock (PLE-88) off/on A/B during a live PS5 stream on SM-S908B

Follow-up of PLE-88 (Wi-Fi low-latency lock landed, harvested), serialized after PLE-79/PLE-116.
One A/B pair, `stream_wifi_low_latency_lock` the only pref that differs, same phone, same console,
same on-device build, 2026-09-16 ~07:10–07:14 UTC.

**Headline: the lock does exactly what it says (acquired with the stream, released on BACK,
confirmed by tag and by the platform's own active-time counter) and changes nothing measurable
about latency or frame-arrival jitter on this AP in a single 15 s pair. Power could not be measured
— the phone is on AC power for the whole ADB-tethered session, and Android does not accumulate
`batterystats` load while charging.**

## Method

`scripts/dev/ab/ab.sh <name> 0 <prefs.xml>` (untouched only — this ticket is about the lock, not
input-thread pacing): leave any live stream with BACK, force-stop, write `shared_prefs` through
`run-as` and byte-compare it back, launch, lock landscape, tap the PS5-466 host tile, wait for the
Takion init acks, settle 25 s, dump `gfxinfo`/`display`/`window`/threads/thermal, record a 15 s
`chiaki_trace.cfg` Perfetto trace, pull everything. `summarize.py` produced the latency/jitter table.

Prefs: `wifioff` = the pulled base prefs unchanged (`stream_wifi_low_latency_lock` absent →
`Preferences.kt` default `false`); `wifion` = base + `stream_wifi_low_latency_lock=boolean:true`
(confirmed in `wifion_prefs_on_device.xml`, `<boolean name="stream_wifi_low_latency_lock"
value="true" />`).

Around each `ab.sh` call, beyond the harness's own captures:

- `adb shell dumpsys wifi | grep -iA3 -i lock` — once while the stream is settled+resumed (mid-scenario,
  right after `ab.sh` returns, before the app is backgrounded) and once ~3 s after sending BACK to
  leave the stream (same as the *next* scenario's own leave-stream step, done manually here so the
  release is captured for the *current* scenario instead of silently happening inside the next
  `ab.sh` call).
- `adb shell dumpsys wifi | grep -A2 mWifiLockStats` before and after each scenario, to read the
  platform's own `low_latency_active_time_ms` accumulator (system-wide, not per-app, but a second
  independent signal for "how long was a low-latency lock held").
- `adb shell dumpsys batterystats --reset` before each scenario, `dumpsys batterystats --charged`
  after, grepping the Wifi/Power sections.
- `dumpsys thermalservice` pre/post — already part of `ab.sh` (PLE-134), reused as-is.

## Results

### Wi-Fi lock lifecycle

| check | `wifioff` | `wifion` |
|---|---|---|
| pref on device | `stream_wifi_low_latency_lock` absent (default `false`) | `<boolean … value="true" />` |
| `Locks held:` while `StreamActivity` resumed | *(empty)* | `WifiLock{com.metallic.chiaki:StreamWifiLowLatency type=4 uid=1000 workSource=WorkSource{10182 com.metallic.chiaki}}` |
| `Locks acquired: … full low latency` (cumulative, system-wide) | 7 → 7 (no change across the scenario) | 7 → 8 (+1, this scenario's acquire) |
| `Locks acquired`/`Locks released` after BACK | still 7/7 | 8/8 — **released**, matches the acquire |
| `Locks held:` ~3 s after BACK | *(empty)* | *(empty)* — lock gone |
| `mWifiLockStats.low_latency_active_time_ms` before → after | 2337 → 2337 (n/a, not exercised) | 2337 → 60083 (**+57 746 ms**) |

The +57.7 s delta in the platform's own active-time counter lands squarely inside this scenario's
wall-clock window (launch → BACK ≈ 65 s, of which the lock is only held from the Takion handshake to
BACK — the rest is app launch/tile-tap before `StreamActivity` resumes), and no other app on the
phone took a low-latency lock during either scenario (`Active lock owners` unchanged apart from
chiaki's own uid). **Verdict: the lock is acquired exactly when the setting is on and the stream is
active, and released when the stream is left — the PLE-88 implementation and its lifecycle hooks work
as designed on-device.**

### Network latency / frame-arrival jitter

The build in this round does not have de-jitter-buffer pacing (PLE-83) or presenter cadence (PLE-108)
enabled in either scenario's prefs (`DJB adj`/`cadence trans` = 0 in both), so the requested "Takion
packet inter-arrival jitter if available" metric has no source this round; the fallback,
frame-arrival jitter from `analyze_ab.py`'s latch-interval spread, is used instead.

| metric | `wifioff` | `wifion` | Δ |
|---|---|---|---|
| queue→present avg / p50 / p90 / p99 / max (ms) | 8.45 / 8.37 / 12.22 / 13.24 / 16.39 | 8.50 / 8.18 / 12.27 / 13.57 / 20.77 | +0.05 avg, +0.33 p99, +4.4 max |
| decode latency mean / p50 / p95 / max (ms) | 7.86 / 7.83 / 9.77 / 17.82 | 8.03 / 7.98 / 9.97 / 21.0 | +0.17 mean, +3.2 max |
| latch interval avg / p90 / max (ms) — frame-arrival jitter proxy | 16.87 / 25.11 / 34.1 | 16.87 / 25.10 / 33.81 | **~0** |
| latch intervals > 25 ms (jitter/miss count) | 138 | 136 | −2 |
| latch rate (Hz) | 58.4 | 58.2 | −0.2 |
| frames queued → latched | 889 → 878 | 886 → 874 | comparable |

**Verdict: no signal.** The frame-arrival-jitter proxy (latch interval avg/p90/over-25ms count) is
identical within noise. The small queue→present/decode max bumps (+3–4 ms) sit inside the band PLE-64's
round-2 baselines already established for this phone/AP (p99 13.16–13.78 ms, max 17.54–21.03 ms across
n=2 15 s baselines) — this is a **single 15 s run per arm, not a statistical study** (per the project's
own standing caveat); a real verdict would need at least two baselines per arm like PLE-64's rounds.
There is no reason from this data to think the lock changes latency or jitter on this AP (a single
2.4 GHz/5 GHz home AP a few meters from the phone — see PS5-466 signal `-57 dBm` in the Wi-Fi
connection-event dump).

Single-run deltas of this size are noise-level next to PLE-64's/PLE-79's repeat-run spread (decoder

attributable to the lock from one pair.

### Power

**Not measurable this round.** `dumpsys battery` shows `AC powered: true`, `level: 100`, `status: 5`
throughout — the phone is tethered to power for the whole ADB session (as it is for every dispatched
capture on this rig), and Android's `batterystats` does not accumulate Wifi/CPU/radio activity while
charging: `dumpsys batterystats --charged` after a `--reset` immediately before each scenario reports
`Wifi kernel active time: 0ms`, "no activity" for every Wifi line, in both arms
(`wifioff_batterystats.txt`, `wifion_batterystats.txt`). PLE-79 hit the identical wall for
`stream_performance_mode` and reached the same conclusion. `dumpsys thermalservice` shows
`Thermal Status: 0` (no throttling) pre/post in both scenarios, and AP/skin temperature deltas
are ≤0.5 °C over the ~1 minute of each scenario — too short and too cool a window to say anything
about power even if `batterystats` worked. The only power-relevant number this round can offer is the
CPU-time proxy above (+2–3 % on the `wifion` single run, inside single-run noise).

## Not proven

- Power draw with the lock on vs off — needs the phone off the charger for a sustained arm; ADB-tethered
  captures on this rig cannot do that (same conclusion as PLE-79).
- A statistically meaningful jitter/latency verdict — this is one 15 s pair, not the ≥2-baseline-per-arm
  round PLE-64 established as the bar.
- Behaviour on a congested or lossy AP — PS5-466 and the phone were both close to the same AP with a
  strong signal (`-57 dBm`); the lock's low-latency mode exists specifically for congested/high-traffic
  Wi-Fi, which this AP is not.
- Takion packet inter-arrival jitter specifically — this build's prefs did not enable the DJB pacing
  path that reports it; only the frame-arrival fallback was available.
