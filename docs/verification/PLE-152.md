Re-run of [`PLE-107.md`](PLE-107.md) on top of PLE-148 (presenter period seeded from the
panel) and PLE-116. Fourteen touched 15 s Perfetto captures on the project phone
(SM-S908B, `192.168.1.105:36437`, Exynos 2200) streaming from PS5-466 (`192.168.1.164`),
2026-09-16 10:35–10:48 local, one `scripts/dev/ab/ab.sh` run each with `touched=1`
(13 stick swipes during the trace — the jitter spike this ticket is about). Build:
`app-debug.apk` from this branch (PLE-107's `stream_video_recovery_strategy` + PLE-148's
seeding), installed with `adb install -r` after `scripts/dev/app-state.sh backup`.
Captures, per-scenario JSON and `summary.json`: `build/dispatch/ple-152/captures/`
(gitignored). Harness frozen for the round in `build/dispatch/ple-152/harness/`.

Arms, n=3 each, on top of the phone's real prefs: `stream_video_pacing_enabled=true`,
`stream_display_refresh_rate=match_stream`, `stream_feedback_stats_log=true`,
`stream_video_pacing_mode=smoothest|balanced`,
`stream_video_recovery_strategy=timeline_shift|flush`; plus `base_touched` (pacing off,

## The precondition holds — and it invalidates the experiment

Every paced scenario logs, at stream start:

    I Chiaki: Video presenter vsync period seeded: 8333333 ns (source=panel, 120.00 Hz)

PLE-148 works: the period is the panel's real 8.33 ms, not the stream's 16.67 ms. The very
next line is the problem:

    I Chiaki: Video presenter smoothest mode using immediate release: 120.00 Hz display
              (timestamped release disabled at 120 Hz)

With a truthful `refresh_hz`, `timestamped_release_eligible()`
(`android/app/src/main/cpp/video-presenter.c:146`) rejects anything `>= 119.0` Hz, so the
presenter falls back to immediate release. Under immediate release every recovery path is
skipped before it can run — `video-presenter.c:292`, `:404` (`drain_immediate_locked()`)
and `:637` all return on `!timestamped_release_enabled` — so neither `timeline_shift` nor
`flush` executes a single line.

`stream_display_refresh_rate=match_stream` does not rescue this. When pacing (or real
PTS) is on, `effectiveDisplayRefreshRateMode()`
(`android/app/src/main/java/com/metallic/chiaki/stream/DisplayRefreshRatePolicy.kt:14`)
overrides the configured mode to `HIGHEST`, so `StreamActivity` pins the 120 Hz mode
regardless: `StreamActivity: Requested display mode 8: 1080x2316@120.00001` in all twelve
paced logcats, `mActiveModeId=8` in every `*_display.txt`. Mode 10 (1080x2316@60) exists
and is what `match_stream` would have chosen. Forcing the panel down from the system side
does not help either: with `settings put secure refresh_rate_mode 0` (Motion smoothness
"Standard") the capture `probe60_shift_smoothest` still logs mode 8, 120.00 Hz and
immediate release — the app's `preferredDisplayModeId` wins. (The setting was restored to
`1` right after that probe.)

The counters confirm it rather than the code alone: **`recovery_flushes 0` and
`recovery_flushed 0` in the last `Feedback stats:` line of all twelve paced scenarios**,
flush arms included (`*_logcat.txt`; the counters are log-line only — see the note below).
In PLE-107 the flush arms logged 13–17 flushes per session.

## Verdict

- **Neither strategy recovers faster, because on this phone neither strategy runs.** With
  the vsync period finally correct (PLE-148), the presenter reports 120 Hz, disables
  timestamped release, and drains every frame immediately; `timeline_shift` and `flush`
  are unreachable code in all twelve paced captures, and the numbers are correspondingly
  identical to each other and to pacing-off. There is nothing to promote — no follow-up
  promote ticket for `flush`.
- **The question is now blocked on the 120 Hz pacing gate, not on the A/B.** The ticket
  that makes this measurable is "pace 60 fps onto a 120 Hz panel (or pin the 60 Hz mode
  when pacing is on)". Until then, `stream_video_pacing_*` and
  `stream_video_recovery_strategy` are inert on the S22 Ultra at its native mode.
- **PLE-107's `shift_balanced2` outlier is dismissed, not reproduced.** Its 82 latch
  intervals > 25 ms was read against paced runs showing 2–5. In this round every arm —
  paced or not — shows 91–116, because presentation is immediate and latch intervals
  follow the 60 fps stream rather than a paced timeline; 82 is an ordinary value for a run
  that presented immediately. Nothing in three runs per arm reproduces an outlier relative
  to its own arm (`shift_balanced`: 91/114/93, widest spread in the round, still within
  the baseline band), and `recovery_flushes 0` everywhere rules out the shift path as its
  cause. Treat it as a run that was not actually pacing, not as evidence about recovery.

## Notes for the next round

- `recovery_flushes` / `recovery_flushed` only appear in the `Feedback stats:` logcat line,
  which needs `stream_feedback_stats_log=true` in the scenario prefs — the first four
  captures of this round were thrown away for missing it. The diagnostics overlay carries
  a `flush-rec` *flag* (`StreamActivity.kt:542`) that only says which strategy is selected;
  it is not a counter.
- The overlay's `hz-match` / `hz-max` flag reports the *configured*
  `stream_display_refresh_rate`, not the effective one after
  `effectiveDisplayRefreshRateMode()` overrides it, so it reads `hz-match` in a session
  that is actually pinned to the highest mode.
- Phone restored: prefs back to the pre-round file (6 keys, registration untouched),
  `secure refresh_rate_mode` back to `1`, app left force-stopped, never uninstalled or
  cleared.
