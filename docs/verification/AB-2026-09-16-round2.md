## Method

metric): `ab.sh <name> <touched> <prefs.xml>` leaves the live stream with BACK, force-stops, writes
`shared_prefs` through `run-as` and byte-compares it back, launches, locks landscape once `MainActivity`
is up, taps the PS5-466 tile at 1160,520, waits for both `Takion received init ack` lines, settles

gestures on the left stick during the trace. `summarize.py` → `<name>.json`, `summary.json`;

### Notes

1. **PLE-6.** The codec accepts the parameter (`CCodecConfig: c2 config diff is c2::u32
   algo.low-latency.value = 1`, `configure() … at tier 0`), and the new metric now sees inside the
   decoder: input→`kWhatDrainThisBuffer` is 8.10 ms mean / 9.78 ms p95 against 8.02–8.23 / 10.05–10.39
   in the two baselines (9.79–10.39 with the extra samples). The −0.3 ms on p95 is inside the band.
   The Exynos decoder already runs this stream at ~8 ms; the low-latency tuning has nothing left to
   remove on the phone.
2. **PLE-16 / PLE-23 at a pinned 120 Hz.** PLE-54 worked: every timestamped run logs
   `Requested display mode 8: 1080x2316@120.00001`, `dumpsys display` stays at `mActiveModeId=8`, and
   the presenter attaches with `using immediate release: 120.00 Hz display (timestamped release disabled
   at 120 Hz)`. The 60 Hz collapse of round 1 (15 ms queue→present, 17 % of frames dropped) is gone, but
   what remains is still a loss on every column:
   - queue→present: PLE-16 inside the band on the average (8.83) but p99 14.03 vs 13.16–13.78; PLE-23
     balanced 9.08 / p99 15.16 / max 21.7; PLE-23 lowest 9.52 / p99 15.63 / max 22.9. Same shape as round
     1's `ple16_ple7highest` (+0.6–0.9 ms): a timestamped buffer waits for its vsync instead of being
     latched at the next one.
   - 3.5–4.2 % of queued frames are never latched (853/887, 854/885, 848/885) against 0.6–1.4 % in the
     baselines.
   - **Decode latency rises from ~8 ms to 13.5–14.3 ms mean, p95 28–34 ms, max 67–72 ms**, in all three
     timestamped runs and in none of the others. `dequeueOutputBuffer` returns track the drain
     (13.66 ms mean for PLE-16), so the app really sees it. It is not output-buffer starvation: the
     codec's `dequeueBuffer` on the output surface never blocks (max 1.6 ms, vs 2.5 ms baseline). The
     only input-side difference is the PTS: the default path queues `timestamp_cur++` (1 µs steps —
     `base_untouched_end` renders at ts 2 057 000…2 943 000 ns in 1 000 ns increments), the flag queues
     `frame_index / 60 s` (increments of exactly 16 667 / 16 666 µs, 887 frames, zero negative,
     one 33 333 µs gap = one lost frame in `ple23_lowest`). Hypothesis, not proven: CCodec or the Exynos
     component derives an operating rate / display-delay policy from the input timestamps and runs the
     hardware decoder slower (or holds output) when they say "60 fps". A run with an explicit
     `operating-rate` / `priority=0` on the codec would settle it; follow-up filed.
   - PLE-33 partial: PTS increments and one lost-frame gap verified in the 15 s trace; the frame-index
     wraparound (65 536 frames ≈ 18 min at 60 fps) is not reachable in a 15 s window — Not proven.
3. **PLE-59.** The flag does what it says: with it the Takion thread runs 100 % on CPUs 4–7 (2148 ms
   big, 0 ms little) where the baseline splits 1277 ms big / 1680 ms little; the decoder's
   `NDK MediaCodec_` threads were already 100 % on big cores in both. Takion CPU time falls 26 %
   (untouched) and 37 % (touched) because the big cores finish the same work sooner; wakeups are
   unchanged (735.5 and 801.8 per s vs 714–724 and 797–800), as affinity cannot change them. No latency
   column moves: queue→present 8.89 / 7.30, decode 8.45 / 6.03, all inside the bands. What is *not*
   measured is power: a big-core millisecond costs more energy than a little-core one, so the CPU-ms
   drop is not a battery win until a thermal/battery session says so. PLE-36 is covered by the
   `sched_slice` per-CPU split above (`ple59_affinity.perfetto-trace`, `base_untouched_end.perfetto-trace`).
4. **PLE-18 after PLE-52.** The fix delivers exactly one draw. `ple18_dirty_logcat.txt` has the two
   one-shot lines PLE-52 added — `First decoder frame available on main; requesting render` at
   05:25:22.044 and `First decoder frame drawn on GLThread 72` 10 ms later — and then nothing from the
   renderer for the rest of the session. In the 15 s trace the codec queued 887 frames into the
   SurfaceTexture and SurfaceFlinger latched 0 buffers of the stream layer; `freeze_test.sh` gives
   0.000 / 0.000 changed samples (`freeze_ple18_t{0,3,6}.png`, byte-identical screenshots) against
   0.000 / 0.472 for deband continuous on the same scene (`freeze_deband_cont_t{0,3,6}.png`; the first
   pair happened to span a static 3 s of the idle screen). The thread list at capture time has **three**
   threads named `GLThread 72` (tids 5564, 5568, 5602) because chiaki's native output/presenter threads
   are created from the GL thread's `onSurfaceCreated → onSurfaceReady → attachToSurface` and inherit
   its comm; only 5602 — the decoder output thread, 1774 `MediaCodec::dequeueOutputBuffer` /
   `renderOutputBufferAndRelease` slices, woken 4024 times by the codec — ran during the trace. The
   real GL thread (5564) never got a single time slice: after the first frame no `requestRender()`
   reaches it. The SurfaceTexture's queue counter reads 1 after every one of the 887 `queueBuffer`s and
   the codec's `dequeueBuffer` never blocks (max 0.6 ms), which is the signature of a droppable
   BufferQueue replacing the one unacquired buffer on every frame — and a *replaced* frame raises
   `onFrameReplaced`, which `SurfaceTexture.OnFrameAvailableListener` never sees. Whatever the exact
   interleaving, PLE-52's main-looper dispatch did not change the outcome measured in round 1. The
   intended GPU saving is still unmeasurable. **PLE-43: do not flip the default.**
   Deband continuous itself, on this build: codec→present 10.01 ms vs 8.44–8.96 direct (+1.1…+1.6 ms;
   round 1 measured +3.2), 3546 GL swaps at 118 Hz of which 879 carried a new frame, app CPU 19.6 s vs
   16.0–16.1 s.
5. **PLE-15 touched, twice.** Takion wakeups 636.6 and 654.3 per s against 797.5–799.9 (−18…−20 %),
   Takion CPU 1898 / 1996 vs 2052–2128, and **no latency column worse in either run**: queue→present
   avg 7.19 / 7.25 (band 7.37–7.60), p50 6.97 / 7.15, p90 11.05 / 10.77 (10.83–11.26), p99 13.33 / 13.14
   (13.73–13.91), max 14.89 / 15.55 (17.74–17.88); decode 5.86 / 6.15 (5.82–6.29); frames latched
   884/887 and 885/888 (baselines 880/886, 881/885). Together with round 1's untouched `ple15_inputthread`
   (596 vs 715–750 wakeups/s, latency inside the band) this is the confirmation PLE-58 asked for:
   **the −20 % Takion-wakeup win holds under touch with no latency cost; flip `stream_decoder_input_thread`
   to default on.** One observation that is not a latency cost: the overlay redraw count in the window
   was 646 / 700 against 722–752 in the other touched runs (RenderThread 757 / 831 vs 759–859 ms). The
   swipes are 13 adb `input swipe` calls whose timing relative to the 15 s window varies by hundreds of
   ms per run; the stream layer's own latch count was normal in both.
6. **PLE-12 touched.** Overlay queueBuffers 752 vs 722–744 and RenderThread 859 vs 818–847 ms: the
   coalescing does not reduce the on-screen-control redraws at all in this method — the overlay already
   draws at most once per vsync (~50/s during the swipes). Latency columns inside the band (the lower
   `latch>25 ms` count, 72 vs 102–111, is a single run). PLE-39 covered; no reason to promote.

Side observation worth its own ticket: **touch makes the whole pipeline faster.** Every touched run
decodes in 5.8–6.3 ms mean (untouched 8.0–8.5) and presents in 7.2–7.6 ms (untouched 8.4–9.5), with the
decoder's CPU time down 40 % — the phone's touch boost raises DVFS clocks and the hardware decoder path
with it. ~2.4 ms of decode and ~1.2 ms of queue→present are on the table for an untouched session if the
same clocks can be requested (ADPF `PerformanceHintManager`, `operating-rate`, or sustained-performance
mode); follow-up filed.

## Harness lessons

- `mkprefs.py` writes the type token verbatim: it must be `boolean`, not `bool`, or Android ignores the
  key and the scenario silently runs at defaults (the README example says `bool`). Check
  `<name>_prefs_on_device.xml` for `<boolean` before trusting any `on` run.
- chiaki's decoder output and presenter threads do not set their own names; they inherit the comm of
  the thread that created them (`metallic.chiaki` on the direct path, `GLThread N` on the deband
  path). The `main CPU ms` and `GL CPU ms` columns therefore include the video output thread (~300 ms
  per 15 s), and a thread named `GLThread` in a trace is not necessarily the GL thread.
- Never move or rename capture files while a capture batch may still be running; rename before
  re-capturing, or capture under new names.
- The harness moved to `scripts/dev/ab/` ran unmodified against the phone; no path fixes were needed.
