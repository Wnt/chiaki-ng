# PLE-128 — de-jitter stage 0 on the Galaxy S22 Ultra

Eight valid 15 s Perfetto scenarios on the project phone (SM-S908B, serial
`R3CT30WLVFV`, Wi-Fi ADB `192.168.1.105:36437`) streaming from PS5-466
(`192.168.1.164`), 2026-09-16 09:28–09:48 UTC. The PS5 was probed immediately
before the round and reported `ready`. The measured build was commit `11b91abe`;
the installed APK's SHA-256 is
`b744fdb057063aeb996f4b97d0ab4bc513f48a96205fbb07246fc7fcdb4b49ad`.

Artifacts are in `/home/wnt/gta6/build/dispatch/ple-128/captures/`: traces,
logcats, prefs read back from the device, display/SurfaceFlinger dumps, thermal
snapshots, per-scenario JSON, `summary.json`, and `summary_table.md`. The frozen
`scripts/dev/ab/` harness is under `.harness/` at workspace commit
`466a0aba847b641249e3bcb50f239b089424ab2f`; `summary.json` records the same SHA
and round name `ple-128-stage0`.

## Method and scenario matrix

`stream_feedback_stats_log=true` in every scenario so the PLE-127 two-second
window line was present. Performance mode, low-latency mode and real-PTS were
explicitly off in the prefs files rather than inherited from the phone. The
instrument-only policy remained in force; this ticket did not enable or
implement `DEJITTER`.

| scenario | panel / input | relevant override |
|---|---|---|
| `dj_base_120`, `_2` | 120 Hz, untouched | direct presenter; two clean baselines |
| `dj_base_60`, `_2` | 60 Hz, untouched | direct presenter, `match_stream`; two clean baselines |
| `dj_base_60_touched` | 60 Hz, 13 swipes | D2/touch control |
| `dj_reorder_off_60` | 60 Hz, untouched | `stream_takion_video_packet_reordering_disabled=true` |
| `dj_loaded_60` | 60 Hz, untouched | bidirectional TCP load between CT950 and the phone for the whole run |
| `dj_paced_flush_120` | 120 Hz, untouched | balanced pacing, `stream_video_pacing_high_refresh=true`, recovery `flush` |

The Samsung normally starts `StreamActivity` at 120 Hz and applies
`match_stream` only after the presenter is seeded. In the first probe,
SurfaceFlinger reached 60 Hz but the presenter retained its logged 120 Hz seed.
For the valid 60 Hz scenarios above, Samsung's `secure refresh_rate_mode` was
temporarily changed from `1` to `0` before launch. Every valid 60 Hz log then
said `source=panel, 60.00 Hz`, and every display dump had the 60 Hz active mode.
The system setting was restored to `1` after each chain.

No second Wi-Fi client was available. The loaded substitute kept a TCP flow
established from CT950 (`192.168.1.114`) to the phone while the phone sent an
infinite stream in the reverse direction to prevent Android netcat from exiting
on stdin EOF. It transferred 2.7 GB in 88 s and reached 30.5 MB/s. This is real
AP/phone-link congestion, but it is not the design's exact second-device load.

The decisive result is not a small threshold correction: every clean arm hits
both the 32 ms depth cap and the histogram's 64 ms last bucket. The clean-LAN
distribution is already censored, so neither touch, congestion nor packet
reordering can be distinguished once steady state reaches the cap. Stage 1 must
not use the provisional constants or this clock recovery unchanged.

The final Perfetto summary is consistent with the round being otherwise valid:
the two 120 Hz direct baselines had queue-to-present averages 7.80–7.95 ms and
p99 12.43–12.54 ms; the two 60 Hz direct baselines had averages 14.19–15.02 ms
and p99 26.01–26.21 ms. All eight valid traces contain 868–889 video codec input
frames, no reorder timeout, loss clamp, stale drop or IDR request.

## P0 verdicts

| criterion | verdict | evidence |
|---|---|---|
| **P0-a** | **PASS only mechanically; censored** | `dj_base_60` and touched both settle at `err` p99 = 64 ms, a 0 ms difference. Their observed ranges also end at the same cap. This cannot validate the upstream measurement point because the histogram has lost the difference it was meant to test. |
| **P0-b** | **FAIL** | Every clean baseline exceeds 4 ms in its first reported window and reaches p99 = 64 ms / `D_target=32 ms`. The design's floor/cap and anchor-slew assumptions are wrong for the measured source clock. |
| **P0-c** | **PASS on the literal ≥8 ms threshold, FAIL as a sensitivity test** | The loaded arm has p99 44–64 ms, but the clean baselines already reach 64 ms. A 2.7 GB, 30.5 MB/s load cannot be separated from the clean steady state, so the statistic as logged supplies no usable congestion signal. |
| **P0-d** | **FAIL** | Reorder-off p99 is 15–64 ms versus clean 21–64 and 37–64 ms; the ranges overlap and all reach the cap. Queue-to-present p99 is likewise 25.89 ms versus 26.01/26.21 ms. Hop 3 is not measurably separable on this clean LAN. |
| **P0-e** | **PASS with the required 120 Hz adaptation** | `dj_paced_flush_120` logs `timestamped_release=enabled`, no immediate-release fallback, 24 `Video presenter DJB` windows, and final counters `recovery_flushes 28`, `recovery_flushed 7`. This is direct evidence that the paced/recovery path executes. A paced 60 Hz arm is not constructible with current policy because enabling pacing selects the highest display mode. |

Overall stage-0 verdict: **stop and rescale/fix the cadence clock before stage
1**. P0-b and P0-d fail; P0-a/P0-c are rendered non-discriminating by
saturation. PLE-142 must not treat 4/32 ms and the current anchor slew as
hardware-calibrated constants.

## D1, D3 and paced-path checks

* **D1 / PLE-119:** the paced prefs file stores
  `stream_real_video_timestamps=false`, but the current session boundary makes
  pacing imply real timestamps (`realVideoTimestamps || pacingEnabled`). The
  hardware log confirms `Frame-index video timestamps enabled at 60 fps`.
  Therefore the unsafe pacing-plus-synthetic-PTS combination is unreachable on
  this build; the original ≥1 s p99.7 failure cannot be reproduced. The old DJB
  still sometimes reaches 32 ms, but its logged p99.7 is 16–64 ms, not the D1
  arithmetic failure.
* **D3 / PLE-120/127:** the direct 60/120 Hz arms each emit 24–26 stage-0
  windows. Arrival/cadence instrumentation now runs outside paced mode, so the
  original “zero samples” D3 does not reproduce after the fix.
* **Paced execution:** `dj_paced_flush_120` is at the real 120 Hz panel period,
  logs timestamped release enabled, has zero fallback warnings, and exercises
  recovery hundreds of times (`summary.json`: 454 flush decisions, 109 frames;
  final cumulative feedback line: 28 transitions, 7 frames).

## Harness and instrumentation limitations

* PLE-127 logs `err` p50/p99, `D`, `D_target`, decode EWMA and drops. It does
  **not** log PLE-108's `J` (inter-arrival deviation) or `G` (gap count), and
  those values cannot be reconstructed from the aggregate `err` percentiles.
  This round therefore does not produce the ticket description's requested
  baseline `J/G` distribution.
* The frozen `summarize.py` does not parse `Video presenter DJB D=...` window
  lines into JSON; its `DJB target` column is the older `DJB adjusted` parser.
  The stage-0 table above was extracted directly from each preserved logcat.
* A paced timeline-shift control was captured twice. Both traces had 883 codec
  input/decode slices but no SurfaceFlinger codec `queueBuffer` slices, so the
  PLE-150 guard correctly marked them failed. The last attempt and first failed
  JSON are preserved under `captures/invalid/`; they are excluded from the
  successful final no-argument summary. The flush arm is the only valid paced
  trace in this round.

## Phone state after the round

The stream was exited with BACK. The pre-round shared-prefs file and the final
on-device readback compare byte-for-byte equal; registration remained present.
`secure refresh_rate_mode` is restored to `1`, rotation is `free`, and the app
is no longer streaming. The measured APK remains installed with `install -r`;
the app was never cleared or uninstalled.
