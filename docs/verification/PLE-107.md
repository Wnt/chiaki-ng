# PLE-107 — flush-on-transition vs timeline-shift, measured on the phone

Nine 15 s Perfetto captures on the project phone (SM-S908B, `192.168.1.105:36437`,
Exynos 2200) streaming from PS5-466 (`192.168.1.164`), 2026-09-16 06:12–06:24 UTC, one
`scripts/dev/ab/ab.sh` run each with `touched=1` (13 stick swipes during the trace — the
jitter spike this ticket is about). Build: `app-debug.apk` from commit `91605892`
(`installed with adb install -r`). Captures and per-scenario JSON:
`build/dispatch/ple-107/captures/` (gitignored), `summary.json` written by
`scripts/dev/ab/summarize.py`.

## What was compared

`AsyncFrameQueue::push` @`0x3be68` in the GFN binary drops its whole queue on a pacing
transition; the fork instead adds whole vsync periods to `timeline_offset_ns`. The commit
makes that a setting, `stream_video_recovery_strategy`:

| scenario | prefs on top of the base file |
|---|---|
| `base_touched` | untouched defaults (pacing off) — reference only |
| `shift_balanced`, `shift_balanced2` | `stream_video_pacing_enabled=true`, `..._mode=balanced`, `stream_display_refresh_rate=match_stream` |
| `flush_balanced`, `flush_balanced2` | the same + `stream_video_recovery_strategy=flush` |
| `shift_smoothest`, `shift_smoothest2` | as above with `..._mode=smoothest` |
| `flush_smoothest`, `flush_smoothest2` | the same + `stream_video_recovery_strategy=flush` |

`smoothest` is the arm that isolates the ticket's question: there `timeline_shift` really
shifts the timeline, while `balanced` already drops the head frame instead.

## Verdict: no signal on latency, and flush is not free

- **Recovery strategy does not move queue→present.** shift 10.11 ms avg / 13.32 ms p99
  (n=2) vs flush 10.17 / 13.44 in `smoothest`; 10.03 / 14.08 (n=1) vs 10.15 / 13.47 in
  `balanced`. Every gap is ≤0.2 ms, inside the ±0.4 ms untouched noise band of
  [`AB-2026-09-16.md`](AB-2026-09-16.md). The A/B answers the question with *neither*.
- **Flush costs frames that shift keeps.** The flush arms log 13–17 `recovery_flushes`
  and 4–6 `recovery_flushed` frames per session (`*_session.log`, `Feedback stats:`
  line); the shift arms log `recovery_flushes 0`. With no latency to gain, the tiebreak
  is the discarded picture, so `timeline_shift` stays the default.
- **One unexplained outlier**: `shift_balanced2` has 82 latch intervals > 25 ms and a
  41.6 ms latch p90, against 2–5 in every other paced run. n=1, not reproduced, and
  balanced does not use the shift path — treat it as noise until someone repeats it.
- Both arms of the A/B are paced against a **wrong vsync period** (below), so this
  compares the two strategies under the same wrong assumption, not under a correct one.

## The measurement caveat worth more than the result

Every paced scenario logs

    Video presenter smoothest mode: stream=60 fps display=60.00 Hz timestamped_release=enabled

while `dumpsys display` in the same capture reports `mActiveModeId=8` — 1080x2316@120.00001
(`*_display.txt`, and `StreamActivity: Requested display mode 8: …@120.00001` in
`*_logcat.txt`). The presenter therefore paces on a 16.67 ms period while the Choreographer
fires every 8.33 ms, and its self-correction lands exactly on its own rejection boundary:
`on_vsync` folds an observed period into its EMA only when it is *strictly greater* than
`vsync_period_ns / 2`, i.e. > 8 333 333 ns, and the panel's real interval is 8 333 333 ns
(120.00001 Hz). Whether the period is ever corrected is left to rounding and jitter — not
a state any pacing measurement should be taken in. `timestamped_release`
is also gated off above 119 Hz, which is why the paced path needs `match_stream` at all.
See the follow-up ticket; nothing in the pacing work is trustworthy until the presenter's
period comes from the panel instead of the stream rate.
