### Notes

1. **PLE-6.** The flag does what it says (`configure() … at tier 0` instead of `tier 3
   (low-latency setting disabled)`), but queue→present starts at the codec's *output*, so a change
   in decode latency inside `c2.exynos.hevc.decoder` is invisible here. Measuring it needs
   `MediaCodec::onQueueInputBuffer → dequeueOutputBuffer` pairing per frame (both are in the trace)
   or the PTS→release timestamp delta; follow-up.
2. **PLE-11.** `android_chiaki_thread_affinity_cb` sets nice −10 on the Takion and decoder threads,
   but on this phone every thread of the foreground app already runs at nice −10 (top-app cgroup:
   `Thread-7`/Takion, `NDK MediaCodec_`, `metallic.chiaki` all −10 in every baseline thread dump).
   `setpriority` succeeds and changes nothing. A real boost needs a value below −10 (refused for an
   unprivileged app) or `SCHED_FIFO` via `sched_setscheduler`, which Android also refuses; the
   remaining lever is affinity to the big cores, which this flag does not set.
3. **PLE-16.** With real 60 fps timestamps SurfaceFlinger's layer-history heuristic switches the
   panel to the 60 Hz mode (`mActiveModeId=10`), and at 60 Hz 17 % of decoded frames are never
   latched (two arrive in one vsync period, the older is dropped). Pinning 120 Hz with PLE-7
   `highest` removes most of the drop but the average is still 0.6–0.9 ms above the baseline
   and p99 is 1 ms higher — timestamped buffers wait for their vsync instead of being latched at
   the next one. Not promotable as is.
4. **PLE-17.** `recvmmsg` batching is confirmed active (`Takion fixed receive pool enabled (128 x
   1500 bytes, recvmmsg batch 16)`), but the Takion thread still wakes 748 times/s versus 715–750
   in the baselines: at ~30 Mbit/s the packets do not arrive in bursts, so each wakeup still drains
   one datagram. The only flag that cut Takion wakeups was PLE-15's input thread (596/s), which moves
   the decoder hand-off off the receive thread rather than batching receives.
5. **PLE-18.** In `RENDERMODE_WHEN_DIRTY` the GLSurfaceView never swaps after the stream starts:
   0 `queueBuffer` on the GL thread and 0 `latchBuffer` of the stream layer during the 15 s trace,
   GL thread 333 ms of CPU, while the codec still delivered 884 frames to the SurfaceTexture. A
   direct freeze test (`freeze_test.sh`: three screenshots 3 s apart, sampled pixel diff) gives
   0.000 changed samples with the flag on versus 0.470 / 0.286 with continuous rendering on the
   same build and scene (`freeze_ple18_t{0,3,6}.png`, `freeze_deband_cont_t{0,3,6}.png`). The
   `onFrameAvailable → requestRender()` chain in `DebandRenderer`/`StreamActivity` does not produce
   a draw on this device; that is a bug to fix before the flag can be measured for its intended
   GPU saving. Both deband scenarios only became runnable because of `860f2213` — the four GLSL
   strings were `const val`s beginning with a newline, and the ANGLE/Vulkan GLES implementation
   this phone uses for the app (`libEGL: Couldn't find an OpenGL ES implementation`, `ANGLE-Submit`
   / `ANGLE-Worker` threads, `RendererVk` slices) rejects `#version` on line 2 with
   `Shader compile failed: #version directive must occur on the first line of the shader`,
   crashing `GLThread` (attempt 1, `deband_on_fail.png`, `ple18_dirty_fail.png`). The fix is
   `trimIndent()` on the four strings.
6. **PLE-19.** The flag only changes the minimum spacing of controller-state feedback packets; the
   untouched capture sends none, and the lib logs nothing about the interval. Prefs on device were
   verified, the video path is unaffected, but the 30-minute controller test PLE-45 asks for was not
   run here.
7. **PLE-23.** Both modes log `Video presenter … using immediate release: 120.00 Hz display
   (timestamped release disabled at 120 Hz)` at attach, then enable frame-index timestamps
   (`Frame-index video timestamps enabled at 60 fps`), after which SurfaceFlinger drops the panel to
   60 Hz exactly as for PLE-16 and the presenter's 120 Hz assumption no longer holds: 15–17 % of
   frames are not latched and queue→present nearly doubles. Not captured: PLE-23 together with
   PLE-7 `highest` (the panel pinned at 120 Hz), which is the configuration the presenter was written
   for; follow-up. No `DJB adjusted` line appeared in either 15 s window.

### What can be promoted

- Nothing measured tonight improves queue→present, missed frames or decoder CPU on this phone
  in a clean-LAN steady state; the present path is already at 8.3 ms average with a 12 ms p90.
- **PLE-15** is the only flag with a measurable win (Takion wakeups −20 %) and no cost in any
  column; it is a candidate for default after a touched/gameplay run confirms the latency columns.
- **PLE-7 `highest`** is neutral alone and required by PLE-16 and PLE-23; PLE-16/PLE-23 must not be
  promoted while they let the panel fall to 60 Hz.
- **PLE-18** must be fixed before it is measured again; **PLE-8/9/20** need an induced-loss or
  induced-reorder session (PLE-40) to show anything, and **PLE-6** needs a decode-latency metric.
- The remaining flags (PLE-10, 11, 12, 13, 14, 17, 19) show no signal in this method; promotion
  would rest on reasoning, not on these numbers.

## Harness lessons

- Lock landscape only after `MainActivity` is in the foreground; `wm user-rotation lock 1` on the
  launcher is reset by Samsung's portrait-only home screen. Every scenario must share one
  orientation (the portrait capture had a different SurfaceView size and cannot be compared).
- Leave the stream with BACK before `force-stop`, otherwise the next connect gets "Remote Play on
  Console is already in use" and the reconnect dialog.
- The host list tile is at 1160,520 in landscape and 998,232 in portrait.
- `summarize.py` must read logcat with `errors="replace"`: one capture contained a non-UTF-8 byte.
- Background shells do not survive a headless worker's turn end; run capture chains in the
  foreground with a bounded timeout, three scenarios per call.
