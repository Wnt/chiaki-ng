# PLE-172 — Confirm operating-rate 960 on the default path (n=2) and promote `stream_decoder_operating_rate_default` (2026-09-16, 08:34–08:44 UTC)

Follow-up of [`PLE-116.md`](PLE-116.md) (headline round, real PTS + operating-rate sweep) and
[PLE-167](https://linear.app/pleikkari/issue/PLE-167) (which wired `stream_decoder_operating_rate_default`,
default off, and raised the real-PTS auto switch's rate to 960). PLE-116 never exercised the default-path
setting itself (it measured `rate960_nopts_untouched` by hand with `stream_decoder_operating_rate=960`
explicit, no default-path flag existed yet); this round is that flag's own A/B, then the promote decision.

**Headline: pass.** Two untouched + two touched captures each of baseline vs
`stream_decoder_operating_rate_default=true`, same build, same phone, same PS5. Untouched: decode mean
7.65–7.95 → 6.74–6.77 ms, p95 9.82–9.93 → 8.39–8.40 ms, q→present avg 8.49–8.51 → 7.70–7.75 ms, decoder CPU
4523–4735 → 4351–4397 ms — every column below PLE-116's `rate960_nopts_untouched` reference (7.78 / 6.83 /
8.43) and never-latched does not rise (0.23–1.13 % vs 0.90–1.70 % baseline). Touched: decode mean
6.01–6.02 → 4.85–4.97 ms, p95 8.80–8.84 → 7.59–8.10 ms — matches PLE-116's `rate960_touched` reference
(4.91 / 7.62) almost exactly. The one soft spot: touched queue→present avg is noisy, one treatment run
(8.34) sits above the same-round baseline band (7.74–7.85) while the other (7.79) sits inside it — see
"Caveat" below. Default flipped to on in `Preferences.kt` / `preferences.xml` (PLE-65 pattern: one commit,
setting stays user-switchable).

## Method

`scripts/dev/ab/round.sh ple-172-round` froze the harness first (PLE-170 protection against a concurrent
`ab.sh` edit). `mkprefs.py --pull-base` showed the phone's persisted prefs still carried
`stream_performance_mode=true` and `stream_real_video_timestamps=true` from an earlier round (the PLE-116
lesson: stored prefs ≠ shipped defaults). Both scenario files pin `stream_performance_mode=false` (shipped
default) and `stream_real_video_timestamps=false` — real PTS is deliberately off so the auto switch (which
now also requests 960, per PLE-167) cannot fire and confound the default-path flag's own effect; this
isolates exactly what PLE-167 added: `stream_decoder_operating_rate_default=true` on the plain 1 µs-PTS
default path.

- `prefs_base.xml`: `stream_performance_mode=false`, `stream_real_video_timestamps=false` (no operating-rate
  request — matches PLE-116's plain `base_*` scenarios).
- `prefs_ratedefault.xml`: same plus `stream_decoder_operating_rate_default=true`.

Eight scenarios, `scripts/dev/ab/ab.sh <name> <touched> <prefs>`, one `device.py run PLE-172` reservation
for the whole round: `base_untouched_{1,2}`, `ratedefault_untouched_{1,2}`, `base_touched_{1,2}`,
`ratedefault_touched_{1,2}` (touched = 13 stick swipes during the 15 s trace). `summarize.py` (no arguments)
at the end produced the table below; `never-latched` (not a `summary_table.md` column in this branch's
harness revision, PLE-161/182 changed the presenter config, so it was computed the PLE-116 way,
`1 − (latch_interval.n + 1) / queueBuffer_by_thread['NDK MediaCodec_']`, from each scenario's `.json`).
Flag application verified per scenario from `<name>_prefs_on_device.xml` and the logcat:

| scenario prefix | prefs on top of defaults | logcat evidence |
|---|---|---|
| `base_*` | `stream_performance_mode=false`, `stream_real_video_timestamps=false` | no `Decoder operating-rate override` line, no `Frame-index` line |
| `ratedefault_*` | + `stream_decoder_operating_rate_default=true` | `Decoder operating-rate override: operating-rate=960 frame-rate=60 (default-path setting)` |

Restore: after the round, the phone's `shared_prefs` was written back to the pulled `base_prefs.xml`
(original values, `stream_performance_mode=true` / `stream_real_video_timestamps=true` included) and
verified byte-identical (`diff base_prefs.xml restored_prefs_on_device.xml` → no output), rotation freed,
app force-stopped.

## Caveat: touched queue→present avg is noisy

One touched treatment run (`ratedefault_touched_1`, 8.34) sits 0.49 ms above the same-round baseline band
(7.74–7.85); the other (`ratedefault_touched_2`, 7.79) sits inside it. `queue→present` measures from the
codec's output through the presenter to the display, a stage the operating-rate setting does not touch
(PLE-55's decode-latency metric — decode mean/p95 — is what pairs with the MediaCodec slices the setting
actually changes); the presenter chain changed twice since PLE-116 (PLE-148 vsync-period seeding, PLE-182
paced release at 120 Hz), so day-to-day drift in this column is plausible and the same-round baseline
(7.74–7.85) is itself already at/above PLE-116's baseline band (7.28–7.74), i.e. the whole round runs
slightly "hotter" in this column regardless of arm. Treated as noise on n=2, matching PLE-116's own
precedent (`rate1920_touched`'s q→p avg was also called "noise until repeated" for a single 0.3 ms excursion).
Follow-up filed below to repeat the touched arm with a larger n if this needs to be nailed down further.

actually acts on) and never-latched pass cleanly and also match PLE-116's reference; touched q→p avg is
inconclusive on n=2 but is explained by a same-round baseline shift not present in the treatment-only
